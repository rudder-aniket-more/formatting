## 3. Steps

Each step is one PR with its own parity or test evidence. **Output change** means a number visible in a report moves; such steps need the named owner's sign-off first.

### Phase 0 — conformed layer (built, unreleased)
1. **Tier 3:** fold `int_plan_year_months` into `int_employee_months`; merge `int_employee_allowances_monthly` into `int_employee_classes_resolved_monthly`; merge `int_dependent_onboarding_periods` into `fct_dependent_coverage`. *No output change.*
2. Apply the decided rules (D-A, D-B, D-C, B4, B5) in the conformed layer.
3. `dbt build` on a PR schema; the guard tests and unit tests must be green.

### Phase 1 — quick wins on live models
1. **B1:** `mrt_ops_and_projected_premium` joins rate year = plan year + 1. **This is a live bug; do it first.** In the same PR, fold `int_requested_rate_change` (T2) and add the I5 empty-carrier guard.
2. **T1:** delete `int_plan_pricing_zip_majority_fips` (repoint Issuers & Plan Counts); replace `int_fips_county_map` with a group-by of `int_plan_pricing_zip`. *No output change*: verify with the parity macro.
3. **T2:** fold `int_care_preferences` into Main Enrollment.
4. Add the missing grain tests: `int_employee_enrollment_base` (B10), `int_plan_pricing_with_fallback` (I4).

### Phase 2 — cutover of the five LCSP-family reports (per report)
Run the parity analysis, get owner sign-off, switch to `latest_version: 2`, keep v1 for 30 days. PCORI goes first and Compliance last. Compliance and PCORI move to `exports/`.

### Phase 3 — clean-up
Delete the 26 replaced models and the five v1 files. Add `fct_` to the orphan-cleanup prefixes after confirming no non-dbt `fct_*` objects exist.

### Phase P2 — enrollment and employer domains
1. Promote `int_employee_enrollment_base` → `fct_enrollments`. Add named flags: `is_latest_for_employee`, `is_latest_in_oep_year`, `is_latest_in_coverage_year`, `is_latest_ops_in_plan_year`, `is_latest_priced_in_plan_year`. Fold `int_ops_latest_enrollment` into them. Repoint the six enrollment marts at the flags. **Each mart keeps its own rule.**
2. Promote `int_employer_master` → `dim_employers` with both NAICS mappings. Rebuild `int_current_month_active_employers` and `int_participation_employers` as filters over it.
3. Merge `int_employer_plan_years` into `int_employer_plan_year_spine`.
4. Resolve the enrollment decisions D-E to D-H and the B8 / B9 tie-break and name fixes.
5. Optional **Tier 4** folds.

## 4. Why some models stay separate

Consolidation is only right when the logic is the same, or should be. These stay separate on purpose:

| Kept apart | Same grain? | Why not merge |
|---|---|---|
| The six enrollment marts | employee × year (mostly) | Their "latest record" rules are **deliberate business variants**: per employee overall, per OEP year, per coverage year, latest priced, and the 2025 in-flight exception. Merging them would change row counts. They share the base (`fct_enrollments`) and differ only in the flag they filter on. |
| Employer Level Details vs Participation | employer × plan year | Different populations (demo kept vs dropped; per-OEP vs zero-filled years) and different measures: "employees" means *eligible as of a date* in one and *employed all year* in the other. They share `dim_employers` instead. |
| Headcount, eligible and enrolled employee models | employer × plan year | Three different measures, each correct for its report. Four definitions of "enrolled / covered" exist across the project. Put the status list in one `is_coverage_status()` macro so the variants are explicit, but keep the measures apart. |
| Age-transition marts | insured person, today | Not plan-year scoped; they already share one base. |
| Snapshot chain | snapshot date | Incremental history with a seeded backfill; it cannot be rebuilt from the facts. |
| Payment chain (7 models) | expectation / transaction | One complex reconciliation; each step is testable on its own. |
| Plan / pricing models | plan, zip, age | Each is a distinct grain with reused rules. |
| 35 staging models | source table | One per source table by rule. |

## 5. How to read the CSV

| Column | Meaning |
|---|---|
| Current model, Folder | The model as it is today (new models have Folder `-` or their new folder) |
| Current consumers (count / list) | Who `ref()`s it today, from the dbt manifest |
| Action | Keep · Replace · Rebuild · Merge · Merge (exact duplicate) · Fold into consumer · Promote · New |
| Target / merged model | Where it ends up. **Rows with the same target are merged together** |
| Merge group | Links the row to §2 |
| Logic difference | How this model's logic differs from the others in its group |
| Recommended steps | What to do, in order |
| Reason | Why combine, or why keep separate |
| Output change? | Whether a report number moves; points to the B / D-x items |
| Sign-off needed | Who must approve before it ships |
| Risk / Phase / Status | Low / Medium / High · 0, 1, 2, 3, P2 · Built, Proposed, Optional, Keep |
